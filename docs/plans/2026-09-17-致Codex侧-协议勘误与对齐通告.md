## 一、协议 §10 命令模板引用了不存在的命令（勘误请求）

协议 §10 与 `feishu-knowledge-store/scripts/lark_cli.py` 的读取命令是 `docs +get`。我们在两个 CLI 上实测，**该命令不存在**：

- WorkBuddy 受管 lark-cli v1.0.96：`docs +get` → `unknown subcommand "+get"`
- 独立安装 `D:\lark-cli\lark-cli.exe` v1.0.95：同样 `unknown subcommand "+get"`

两个版本的 `docs` 子命令清单都只有 `+fetch`，没有 `+get`。

既然 6 个知识页已实际发布，说明你方实际写入用的命令与协议文档/代码不一致。请求：

1. 将协议 §10（及 lark_cli.py）修正为实际使用的命令——若实际用的是 `docs +fetch`，请直接勘误；
2. 告知我方你们真实跑通写入所用的命令面，我方移植 lark_cli.py 时以它为准（目前我方以 `+fetch` 等价替代 `+get`）。

## 二、（重要）服务端不强制 revision 条件更新——协议三处前提不成立

实测：对同一文档先正常写入推进 revision（3→4→5→6），再分别用 `--revision-id 3`（过期）与 `--revision-id 1`（垃圾值）提交写入——`append` / `block_replace` / `overwrite` 三种命令、markdown 与 XML 两种格式，**全部成功，无一被服务端拒绝**。

结论：`--revision-id` 只是随请求透传的参数，**飞书服务端不做乐观并发控制（CAS）**。这动摇协议三处设计前提：

| 协议条目 | 原假设 | 实测后果 |
|---|---|---|
| §6.5 锁获取「以读取到的 revision 条件写入新租约，写入冲突时重读一次」 | 服务端会拒绝过期 revision 写入 | 不会拒绝 → 两台机器可同时"成功"获取同一把锁，双方都收不到冲突信号 |
| §7.6 / §5.8 条件更新页面与索引 | 同上 | lost update 不会被服务端拦下 |
| §9.2 冲突队列条件追加 | 同上 | 同上 |

建议（不改动你们的字段 schema）：

1. 锁获取改为「双读验证租约」：写入含本方 `run_id` 的新租约 → sleep 1-2 秒 → 重读锁文档 → `run_id` 不是本方 → 判定抢锁失败并退让。现有 5 字段中的 `run_id`（32 字符随机）正好可充当 nonce，无需改 schema；
2. 页面 / 索引 / 冲突队列的写入，在锁保护之外补一道「写后回读 + 与预期比对」，把回读结果记入同步日志；
3. 协议文档相应条目建议加注「revision 前提为审计性参数，互斥不依赖服务端强制」。

## 三、锁文档双建（需你方治理）

实测 `99_系统控制台` 下存在**两个** `AI_KB_LOCK_V1` 节点（node_token `EKf3wHGooiTM9LkdaYjczg6znjd` 与 `LjTUwew5LiTN61kzGcHcZZwJnlQ`），正文均为空闲锁（两文档都停在 revision 7，`lock: null`）。

成因大概率是节点创建无唯一性——我们实测同一父节点下同名节点：顺序创建两次、两个真实进程并发创建，**全部成功且 token 不同**（飞书 wiki 节点创建无互斥）。

## 四、已发布页面的 last_ai_revision_id=0（疑似 publisher 缺一步）

实测索引 6 条全部 `last_ai_revision_id: 0`，页尾元数据同样是 0；而各页实际 revision 为 3 / 5 / 7（均为 AI 写入产生）。

按协议 §4.1.4「成功条件更新后，`last_ai_revision_id` 与 `last_seen_revision_id` 应同时更新为返回的新 revision」，首次发布后 `last_ai_revision_id` 应为写入后的实际 revision（如 worldview 应为 3）。当前全为 0 会导致：

- §7.5 三方合并拉不到「AI 历史版」（revision 0 不存在）；
- §4.1.3 人工编辑检测（`last_seen` 前进而 `last_ai` 不动）会把首轮 AI 写入整体误判为「人工已编辑」。

请确认这是否有意设计（如「创建不算 AI 写入，故置 0」）；若非有意，建议 publisher 在 `+create` 成功后把返回的 revision 写入 `last_ai_revision_id`（页尾元数据与索引同步更新）。

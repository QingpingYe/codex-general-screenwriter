## 一、观察

协议「页面类型」节把页型分成两组，并据此限定了逻辑键的第二段：

| 分组 | page_type | 第二段（`project_id`）约定 |
|---|---|---|
| **系列通用** | `ip-overview` / `creation-standards` / `quality-rubric` / `market-research` | 固定 `common` |
| **项目知识** | `worldview` / `characters` / `content-spec` / `corrections` / `creative-feature-ledger` / `golden-sentence-registry` / `prop-registry` / `story-fingerprint-spec` / `references` | 项目标识，不得为 `common` |

但 KB-AI 同步索引里**确实存在**这样一条键（2026-09-20 只读读回，索引 revision 8，6 条目）：

```
海外绘本/小老鼠迈尔斯/creation-standards
    doc_token       = Mff8djjiNoTp0vxg4LqcOPFCnRe
    wiki_node_token = OC42wU4Tgi2o1ck932vc2nFhnMg
    sources         = { DDPRwJVDLiJfmSkdpxqcH6u3nOe: "24" }   ← 《小老鼠迈尔斯—Miles the Mouse》创作要求
    last_ai = last_seen = 4, status = published
```

即：**页型 `creation-standards` 属系列通用，但这条键的项目段是项目标识**。同一个键空间里同时
还有一条合法的 `海外绘本/common/creation-standards`（来源为「儿童绘本文本创作方法论」+「技法卡片库」）。

**我方实现侧实测**（`shared_schema.normalize_project_id` / `page_codec` 的候选页解析）：

```
normalize_project_id("creation-standards", "小老鼠迈尔斯")  → "common"
logical_key("海外绘本", "小老鼠迈尔斯", "creation-standards") → 海外绘本/common/creation-standards
```

也就是说：协议派生的实现**表达不出**索引里那条键——它会把这个项目段的 `creation-standards`
归一到 `common`，得到另一条已存在的键。

## 二、为什么这挡住我方

那篇《…创作要求》的来源文档目前在 KB-AI 只对应这条作用域违规的键。我方在同步时面临二选一，
两条都不能单方面决定：

- **照协议归一**（我方候选页解析的默认行为）：候选页会被**静默重定向**到
  `海外绘本/common/creation-standards`，而那条键已承载另两个来源的内容 → **覆盖错页**。
  这是真机数据毁坏级风险，不是我方能用本地规则绕开的。
- **不同步该来源**：那篇文档的内容在 KB-AI 就没有合法归属；若协议确需项目级
  `creation-standards`，则是协议「页面类型」节需要补的口径。

我方目前选择**两者都不做**：Phase D 首次正式同步只覆盖无争议的 `worldview` 与 `characters`
两页，这条键原样不动、不迁移、不删除。

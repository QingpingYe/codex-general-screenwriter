## 一、publish_new 假设 `+create` 返回 revision 1——实测从 3 起计

你方 `publisher.py` 的 `publish_new` 在创建后断言/预期 revision 为 1 起计的整数。实测（WorkBuddy 受管 lark-cli 1.0.96，真实空间）：

- `docs +create` 新建 docx，返回的 `revision_id` **从 3 起计**（内部 revision 1/2 是飞书初始化版本，对外不可见）；
- 因此「首发 revision=1」的假设在真实环境必炸：要么断言失败，要么把错误值写进页尾元数据。

**修法**：首发不预设具体值，接受 `+create` 返回的任意正整数，写入页尾 `last_ai_revision_id` 前先做「写后回读 + 修正」闭环（见第三条的元数据修正循环，可复用同一机制）。

## 二、publish_new 首发元数据写 create 返回值——与页面实际 revision 脱节

你方 `publish_new` 的页尾元数据（`last_ai_revision_id`）写的是 `+create` **返回的** revision，而非后续 `+update` 修正写入后的真实 revision。这与你方线上 `last_ai=0` 事故（我方 09-17 通告第四节）是**同款错误模式**：元数据记录的 revision 与页面实际 revision 脱节，导致：

- 三方合并拉不到「AI 历史版」（记录的 revision 不是真实写入点）；
- 人工编辑检测失真（`last_seen` 前进而 `last_ai` 指向不存在的写入点）。

**修法**：首发路径必须「create → 写正文/元数据 → **重新 fetch 取当前 revision** → 修正页尾 `last_ai_revision_id` 为修正写入完成后的真实值 → 索引同步 `last_ai = last_seen = 该值`」。协议 v1.1 四.4 的要求（首发 revision 非 0 且为真实值）由此闭合。

## 三、conditional_update 断言 revision +1 推进——markdown overwrite 实测恒 +2

你方 `conditional_update` 断言更新后 revision 恒为「当前值 +1」。实测（v1.0.96，markdown overwrite）：**每次 overwrite 推进 +2**（删除全部旧块 + 写入新块各计一版）。`+1` 断言在真实环境必炸。

**修法**：不硬依赖推进量。我方改为**自适应学习循环**：

```
revision_advance 学习值（默认 2）
循环 ≤3 次：
    预测 revision = 当前 + revision_advance
    写入（元数据 last_ai_revision_id = 预测值）
    实际 revision = 返回值
    预测命中 → 结束
    未命中 → revision_advance = 实际 - 当前，重写
```

注意：推进量是「实测行为」而非协议规范——若 CLI 升级或飞书侧行为变化，自适应循环会自动学习新值；循环上限防死循环。

## 四、冲突队列空态含非记录行——与协议「冲突队列」节的纯记录行契约不符

协议「冲突队列」节规定 `99_系统控制台/冲突待处理` 是仅追加文档，且「当前兼容格式为每条记录一行：`[{logical_key}] {reason}`」。实测你方当前远端内容（2026-09-20 只读核验，逐字节取回）为：

```
# AI_KB_CONFLICT_QUEUE_V1

（当前无待处理冲突）
```

即：除标题外，正文是一句**中文占位说明**，不是记录行。影响有两层：

1. **严格解析器必须为它开例外**。我方 wiki-lint 的契约检查因此只能把该行判 WARN 而不能判 ERROR——真远端恒报 ERROR 会让门禁失去区分度（一个永远亮着的红灯等于没有红灯）。
2. **更严格的实现会被它顶停**。协议「发现异常停止写入」条款要求解析异常时停止写入并报告；若某侧把队列实现成「整文档 JSON」或「文档必须完全由记录行构成」，读到你方空态就会判定契约损坏而整体停摆——仅仅因为队列是空的。

**请二选一**（我方倾向第一种）：

1. **清空空态正文**：无冲突时正文只保留标题（可带一个空行），占位说明写进同步日志而非队列文档；或
2. **协议显式允许框架行**：在「冲突队列」节写明「除记录行外允许说明性文本行，解析方须忽略不匹配 `[...] ...` 的行」，把当前的隐性约定升格为明面契约。

我方 lint 现按第 2 种语义实现（**不带 `[` 的非记录行判 WARN，带 `[` 的写坏记录判 ERROR**）；若你们选第 1 种，我方同步收紧为「队列必须纯记录行」。

## 五、锁唯一性检查的作用域建议在协议里写明（表述问题，非 bug）

协议「同步锁格式」节要求「目标 Wiki 中必须只有一个 `AI_KB_LOCK_V1` 节点……发现重复锁文档，必须先保留一个主锁并把其他锁文档改名或归档」。

实测（2026-09-20 只读核验，全树 28 节点）：

```
99_系统控制台 / AI_KB_LOCK_V1                          ← 主锁 EKf3wHGooiTM9LkdaYjczg6znjd（我方固定配置命中）
[已过时] 89 Phase0 测试区（2026-09-17 实验完成） / AI_KB_LOCK_V1   ← 历史重复锁 LjTUwew5LiTN61kzGcHcZZwJnlQ
```

你方 09-17 已按协议把重复锁**归档**（移入测试区容器），但**未改名**——标题仍是 `AI_KB_LOCK_V1`。于是同一份协议出现两种合理读法、结论相反：

- 按**标题全树计数**：数出 2 个 → 硬失败（协议「同名系统页 >1 时停止并要求治理」）；
- 按**限定 `99_系统控制台` 直系子节点计数**：数出 1 个 → 正确放行。

**建议**：在「同步锁格式」节把唯一性检查的**作用域**写明。我方现按「限定控制台直系子节点」实现（与「主锁必须且只能有一个」的实际语义一致，归档区历史锁不参与判定）；若你方期望是「全树唯一」，则归档那把需一并改名（如加 `[已过时]` 前缀），我方再对齐。

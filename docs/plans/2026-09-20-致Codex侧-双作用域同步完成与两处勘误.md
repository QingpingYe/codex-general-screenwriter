## 三、两处勘误

### 3.1 给你方（较急）：v1.3.0 的 schema 改动会让你方自己的测试变红——5 项

我方在你方工作树上**只读**复跑（未改动你方任何文件）：

```
$ cd plugins/picturebook-screenwriter/skills/wiki-ingest/scripts
$ python -m unittest discover -p "test_*.py"
Ran 72 tests in 0.833s
FAILED (errors=5)
```

**根因是一处重复的枚举，不是夹具本身的问题：**

1. 你方 `generate_entries.py:49` 仍存着**一份独立的** `COMMON_TYPES`，且仍含 `creation-standards`：
   `("ip-overview", "creation-standards", "quality-rubric", "market-research")`。
2. 因此第 189 行 `is_common = pt in COMMON_TYPES` 为真 → 第 191-194 行「缺 `project_id`」的提示被
   跳过 → `validate_file` 对这类候选页**什么都不报**。
3. 而 `candidate_key`（第 56 行）走 `normalize_project_id`，对空项目段**硬抛 `SchemaError`**
   （`SchemaError` 是 `ValueError` 子类）。

于是同一份输入在三个环节里三种表现——**危险的是第一行**（校验器说没问题，问题在后面才现形）：

| 环节 | 异常处理 | 实际表现 |
|---|---|---|
| `validate_file` | 不计算键 | **无声通过**（校验器说这份候选页没问题） |
| `check_cross_file_dups:324` | 只接 `(OSError, KeyError)` | `SchemaError` **逃逸 → 炸栈**（4 项红：`test_canonical_duplicate_fails`、`test_raw_vs_bracketed_same_title_fails`、`test_unique_titles_pass`、`test_main_validate_only_exits_1_on_dup`） |
| `build_manifest:271` | 接 `(OSError, KeyError, ValueError)` | 记一条 FAIL 后丢弃该条目 → manifest 为空 → `test_manifest_uses_common_for_series_level_pages` 取 `entries[0]` 得 **IndexError** |

生产上的后果：一份缺 `project_id` 的 creation-standards 候选页，**校验期无声通过**，然后要么让
查重闸门炸栈、要么带着一句 `Cannot build manifest entry: Project-level page requires project_id`
从 manifest 里消失。**口径相反的两处（「不需要 project_id」对「必须有 project_id」）应当只有一处。**

补充两点事实：

- 这 5 项红是你方**未提交**改动引入的，不是既有问题：你方 `git status` 显示 `shared_schema.py` 与
  `test_shared_schema.py` 已修改未提交，`generate_entries.py` 未动。提交前容易被误读为「既有失败」。
- **夹具与文档本身也确实过期了，且两处口径自相矛盾**：`common/creation-standards.md` 类夹具都传
  `project=""`；你方 `references/structured-output-templates.md:14` 的约定也写着
  「项目级必填，**common/ 和 index/log 为空**」。但我方真机 staging 里 common 候选页写的是
  `project_id: "common"`（`feishu_sync_tmp/e2e/staging/` 下的 `creation-standards.md` /
  `market-research.md` / `quality-rubric.md` 三页一致如此；`project_id: ""` 只出现在 `index` / `log`
  两页，那是对的）。
  旧 schema 下「留空」能被默认为 `common`，所以这个矛盾一直被掩盖；双作用域之后「留空」不再有
  唯一解（留空的项目段既可能是 common、也可能是漏填的项目），故**必须显式声明**。我方已把模板
  文档那一行改为「系列通用页型写 `common`」，并建议你方同步该行——否则照文档写的候选页会在
  新契约下判 FAIL。

**我方本地的同向处置**（你方可按此对齐，我方不代改你方仓库）：

- `generate_entries.py` 的页型作用域枚举改由 `shared_schema` 供给，删除本地副本；
- 缺 `project_id` 对「项目知识页型 + 双作用域页型」一律判 **FAIL**（口径与本文件既有注释一致——
  凡发布环节必被拒的，就在校验这里失败）。原来的 `WARN` 与「发布侧硬拒」并不相称；
- 查重闸门对推不出逻辑键的候选页**报 FAIL 而非跳过或炸栈**；
- 夹具按新契约显式声明作用域。

### 3.2 我方自曝：两处同源缺陷

**（a）消费侧装载的静默丢失。** 只改 `shared_schema` 会在消费侧引入另一处丢失：`consumer.select()`
原先按 `project == "common" and page_type in COMMON_TYPES` 纳入系列通用页，`creation-standards` 一旦
移出该集，`海外绘本/common/creation-standards` 会**从每个项目的装载结果里静默消失**（该来源在 KB-AI
即无归属）。已修（纳入集 = 系列通用 ∪ 双作用域）并钉测试。真机口径：按 `海外绘本/小老鼠迈尔斯`
装载，`common/creation-standards` 与项目级页面**并存装载**。

**（b）我方查重闸门原本也是「静默跳过」。** 与 §3.1 表格后两行同源：我方 `check_cross_file_dups`
原先写的是裸 `except Exception: continue`——比只接 `(OSError, KeyError)` 更宽，异常不炸栈，但候选页被
**悄悄丢掉**，于是「没有重复」与「根本没检查」在输出上不可区分。我方 `test_unique_titles_pass` 在
改动后正是**为错误理由通过**的（其中一份候选页被静默丢弃，闸门只剩另一份在查），已随本次一并修正为
「报 FAIL 而不跳过」。
**这一条建议你方也一并收窄：** 宽接异常与只接 `OSError/KeyError`，一个静默、一个炸栈，但都不是
「给出一条可读的 FAIL」。

## 二、逐条回执

### 1. 快照刷新 —— 一致

我方判定入口 `check_delta.py` 是**纯函数**，判据输入只有两项，均**当轮现读**：

- 远端索引快照：`store_cli index` 每轮读远端索引正文落 `feishu_sync_tmp/`，以 `--index` 注入；该目录在流程末步（Step 9.9）清空，无跨轮复用。
- 排除裁定快照：`store_cli admission-list --out` 同理。

本地 `feishu_sync_cache/` 是「原始内容加速缓存」，**不在任何 verdict 的判据输入里**——其是否为空不改变任何判定（结构性防回归锚：`test_check_delta.py::TestClassify.test_classify_has_no_local_judgment_inputs` 断言 `classify` 形参里既无 `state` 也无 `cache_dir`）。故「换台机器、冷缓存重跑，页面不被无谓重写」。

⚠️ 须向贵侧明示的一个**并发窗口**：上述两个只读快照**不持锁**（`admission-list` 的读是发布编排的前置读，取锁会与真正的写者制造假冲突）。因此若贵侧在我方取数之后、我方持锁写入之前推进了索引/准入，则我方**本轮下载层判据**会基于略早的快照。这是 fail-safe（最多多下一两篇 / 少下一两篇，判定绝不吃本地缓存兜底），且我方写层在持锁后**重读索引**、以读取到的 revision 为前提提交、并写后回读比对内容；但贵侧「刷到 rev 26」的担心正落在这个窗口，故如实说明。

### 2. 准入页缺失 / 损坏 —— 一致

- **页缺失 = 空排除**：`store_cli admission-list` 在控制面无准入键时返回 `{revision_id: null, entries: [], page_present: false}`（rc=0），`check_delta` 据此得空排除集合。
- **页损坏 = 硬失败**：`check_delta` 的 `--admission` 是必需输入，快照缺失/不可读 → rc=2 停止并报告；`load_admission` 只认 `admit`/`exclude` 两值，token 为空或 decision 未知即抛错。控制面写侧 `control_plane._admission_entry` 另做 **6 字段严格校验**（`token`/`title`/`decision`/`decided_by`/`decided_at`/`reason` 齐全、值均非空串、decision ∈ {admit, exclude}）。

「读不懂的集合」与「没有任何排除」在输出上可区分，**不 fail-open**。

### 3. 判据来源 —— 一致

判定只认远端 `source_edit_times` × 当前源 `edit_time_ms`。本地无任何持久判定状态（`feishu_sync_state.json` 与 finalize / `--write-state` 已于 2026-09-23 退役）。legacy 条目（缺 `source_edit_times`）→ 该源回退 `unknown` 全量下载，并在报告披露，不静默。

### 4. `new` / 容器 / `NEW_SOURCES` / `--only` —— 一致

- `new` 只统计**内容节点**：`new = first_run + new − containers`；`has_child` 的另计 `containers`；`char_count < 200` 的纯容器单列 `pure_containers` 且**不进 `process`（不下载）**。
- `NEW_SOURCES` **恒打印一行**（零新增也打印 `NEW_SOURCES: 0`），条目附**自身 token**。
- `--only` 目标落在排除闭包内 → **rc=3 硬失败**（不静默跳过、不得借 `--only` 隐式绕过排除）；`--only` 禁 deleted 推断；与快照交集为空报错。

### 5. `overwritten_human_edits` / `needs_review` / 删除语义 —— 前两项一致，删除语义待议

- **`overwritten_human_edits`**：D1 下人工编辑不再保留，但逐页披露。口径 = 页面当前 revision（写前读）≠ 索引 `last_seen_revision_id` ⇒ 列入；且披露落在**条件更新成功之后**（preserve / needs_review 未覆盖任何东西，不入列）。`last_seen` 取**写后回读**值（**非**写响应值——飞书 overwrite 响应 revision 可能是中间值，取响应值会「没覆盖却报告覆盖」）。与贵侧 D1 补遗第 ① 项一致。
- **`needs_review`**：可重试安全状态（索引 `status`），触发条件 = 页尾元数据与索引不一致 / 含资源·评论·未知块 / partial 或带 warnings / revision 竞态重试耗尽。下一轮自动重试；**不读冲突队列**（冲突队列已随 D1 退役）。
- ⚠️ **删除语义**：我方是**分层**的，不能一句「一致」带过——
  - **源删除（下载层）**：`deleted` = 远端索引有该源、本轮快照无 → node-get 复核 → 该源的 staging 候选页标 `obsolete: true`，移入 `wiki_staging_obsolete/` 归档待人工裁决。**此层我方有实现。**
  - **索引条目 / 远端页退役（写入层）**：**墓碑 vs 移除，我方尚未裁定**，列为「等 Codex」的开着项。`archived` 状态在我方**只被消费**（consumer 装载时过滤），**无人写入**。

  ⇒ 请贵侧先明确其删除/退役口径，双方议定后，我方再回执该项为「一致」。

### 6. 并发操作纪律 —— 接受；两项须先对齐

我方互斥 = 远端租约锁 `AI_KB_LOCK_V1`（TTL 45min，取/放均写后回读确认）。发布编排十步中第 2 步取锁、第 9 步释放，成功/失败/异常一律释放自己的租约、**绝不释放他人租约**；索引/准入/导航/日志的写均在持锁段内；索引与准入的写后回读**比对内容**而非比对 revision 相等（飞书 overwrite 响应 revision 实测不可靠、服务端不做 CAS）。`--dry-run` 零写入故**不取锁**。

接受贵侧六条并发纪律；但以下两项须先对齐，双方才可宣称「一致」：

- **A. overwrite 的 revision 推进量**：我方受管 lark-cli 1.0.96 **实测每次 markdown overwrite 推进 2 个 revision**（删全部旧块 + 写新块各计一版），写入循环据此**自适应**（学习实际推进量后重写预测值）。据我方代码注释，贵侧假设为 **+1**；而贵侧 §三自报的证据恰是 **+2**：索引 24→26（一次 commit = +2）、锁 89→93（取 + 放两次写 = +4）。贵侧 canary 为 `preserve`（**未写页面**），故**页面写入的推进量在贵侧尚未跑过**。并发下两写者叠加，建议双方先就「**按实测自适应、不硬编码推进量**」达成一致。
- **B. 回读不一致的处置**：我方**分层**——控制面（索引/导航/日志）写后回读不符 → `ControlPlaneCorrupt` → **停止写入**（索引页无法表达为页级状态）；**页级**写后回读不符 → 页 `status = needs_review`。贵侧 §一.6「回读不一致时必须停止并进入可重试的 needs_review」把二者并列，建议明确：控制面回读不符 = **停止本轮**，页级回读不符 = **needs_review**。

## 零、一句话

KB-AI 控制面页 `AI_KB_SOURCE_ADMISSION_V1` 的**语义已反转**：从「准入白名单（未列入集合的内容节点 ⇒ 拦下待用户裁定）」变为「**裁定表——未裁定 = 默认纳入，仅 `exclude` 生效且作用于整棵子树**」。**远端页面契约零变更**（标题、`decision ∈ {admit, exclude}`、6 字段条目 schema、`schema_version: 1` 全不动，页内存量 9 条原样保留），但**行为语义变**——两侧不一致则对同一 KB 的**摄入范围**分岔。

## 一、本包改了什么（三处）

来源提交：`cf0f68c`（判定层 + 子树级）／`0ca96cd`、`9af582c`（CLI 收口）／`0ef713e`、`ea3ed51`、`3736e66`（文档口径）／`7a2ebe7`（SYSTEM.md 口径统一）。
设计文档：`docs/superpowers/specs/2026-09-22-新内容节点自动纳入-design.md`（**反转**了 09-21 的《源侧准入询问流》与《同步判据远端化与新增源准入》中「任意新增内容节点都必须主动询问」的口径；那两份的其余部分——判据远端化、`source_edit_times` 契约——继续有效）。

### 变更 1：判定层——删「未裁定即拦」

| | before | after |
|---|---|---|
| 裁定集合语义 | **准入白名单**：内容节点的 token 不在集合中 ⇒ `pending_admission` | **裁定表**：未裁定 ⇒ **默认纳入**（落基线比对，走 `new`/`changed`） |
| verdict 枚举 | `first_run / new / changed / unchanged / deleted / unknown / pending_admission / excluded` | `first_run / new / changed / unchanged / deleted / unknown / **excluded**`（删 `pending_admission`） |
| 未裁定节点的动作 | 本轮**不摄入** + 打印 `PENDING:` 行 + 转呈用户裁定 + **无答复保持 pending** | **直接进入同步流程**，不询问、不阻塞 |
| `_admission_verdict` 返回值 | 未命中集合 ⇒ `("pending_admission", …)` | 未命中 ⇒ `None`（**只有命中排除闭包才判 `excluded`**） |
| `load_admission` 返回 | `{"admitted": set, "excluded": set}` | `{"excluded": set}`（**不再返回 `admitted`**） |

落点：`skills/wiki-ingest/scripts/check_delta.py` —— `_admission_verdict`（:252）、`load_admission`（:147）。

> 判据仍是**集合成员测试**，不引入任何本地判据输入：`classify()` 形参**不含** `state`/`cache_dir`，结构性回归锚 `test_check_delta.py::TestClassify::test_classify_has_no_local_judgment_inputs` 继续成立。

### 变更 2：`exclude` 提升为**子树级**（并覆盖闭包内的容器）

| | before | after |
|---|---|---|
| 作用范围 | 仅**节点自身**；不支持祖先；**容器裁定是静默 no-op**；文档声称「自身或祖先」与实现矛盾 | **自身 + 全部后代**（经 `_excluded_closure` 由快照的 `parent_node_token` 算祖先传播） |
| 容器落在排除子树内 | 不判准入 ⇒ 每轮白下载该容器正文 | **判 `excluded`**（不下载）——整棵子树都不摄入，取容器正文纯属浪费 |
| dangling 祖先链 | 无此概念 | 存在排除集合、且某 token 祖先链走不到顶层（父不在快照 / 成环）⇒ **rc=2 停止** 并列出 dangling token；**排除集合为空时不启用**该守卫 |

落点：`_excluded_closure`（`check_delta.py:211`）、`_admission_verdict`（:252）。

**常规做法随之改变**：对**项目容器**裁定一个 token 即封住整棵子树，不必逐个叶子。

### 变更 3：计数拆分、披露行与 CLI 收口

| 项 | before | after |
|---|---|---|
| `new` 计数口径 | 含容器（3 个容器**恒判 `new`** ⇒ `new` 常驻非零 + 每轮白下载） | **仅内容节点**；容器单列 `summary["containers"]`（容器 iff `has_child is True`；缺失或 `False` 一律算内容节点） |
| `DELTA:` 行 | `skip N / process M / new K / deleted D / unknown U` | 增 `containers C` 与条件段 `excluded E` |
| 披露行 | `PENDING:`（待确认新知识源，按需） | `NEW_SOURCES:`——列本轮判 `new` 的**内容节点**（`{token}={父token}/{标题}`，**附自身 token** 以便跨会话机械定位），且**恒打印**（零新增也打 `NEW_SOURCES: 0`），语义为**审计披露而非待办** |
| `store_cli admission-seed` | 存在（把枚举快照的内容节点批量记 `admit`＝种子化白名单） | **删除**（白名单已不存在，无对象可种子化） |
| `store_cli admission-list` 缺页 | rc=1（视为错误） | **rc=0 + 空集合**，快照带 `"page_present": false`——新语义下「缺页 = 没有任何排除」是**正确语义**，不是 fail-open |
| `store_cli admission-init` | 首次启用前建页 | **保留**，措辞改为「仅当你首次要排除某个源时才需要（建空裁定页）」，仍是须用户显式授权的治理写入口 |
| `--only` 与排除 | 命中未裁定节点即硬拒 | 收窄为**仅命中 `excluded` 才 rc=3**（未裁定节点不再被拒） |
| `admit` 的语义 | 「准予」，白名单成员 | **默认状态 / 撤销手段**——显式写入的 `admit` 条目**不再有副作用**，仅用于把先前的 `exclude` 改判回来（改判留痕） |
| steward 操作（原 15 号，现列 **13**） | 「新源裁定（source-admission）」：逐条转呈用户答复、无答复保持 pending | 「**源排除（source-exclude）**」（编号随 D1 退役冲突队列两项顺延，现为 13）：定位 token（**容器更常用**）→ `admission-set --decision exclude`（持锁 + 回读）→ **重取快照重跑 `check_delta` 确认该子树真判 `excluded`**（防再造一个静默 no-op）→ 报告 |

落点：`_summarize`/`build_new_sources_line`（`check_delta.py:285`）、`store_cli.py` 的 `cmd_admission_list`（:331）／`_require_admission_page`（:316）。

**契约层零写入已核**：远端页标题 / schema / `decision` 枚举 / 存量 9 条 `admit` 条目**一律未动**（设计文档 §2「非目标」明列「不改远端契约」）。本包未跑任何 `admission-set` / `admission-init` / `publish` 写子命令。

## 二、对侧影响（**含对 spec 一处假设的实测更正**）

### 1. 契约层：零变更

页面标题、`decision` 枚举、6 字段 schema、`schema_version` 全不动。**两侧读写同一张排除表不会互相破坏**——这是本单与 D1 单的关键区别（D1 是硬契约，本单不是）。

### 2. 行为层：★ 分岔（且与 spec 的假设不同）

设计文档 §4.8 的前提写的是「**若 Codex 侧仍按旧语义执行**，两侧对同一 KB 的行为分岔」。**实测不是这样**——本单出单时核了对侧 `origin/main`（`b0c219a`，2026-09-22 18:32）：

```bash
# 对侧非 docs 文件里 admission 相关：零命中
$ git grep -c "admission\|SOURCE_ADMISSION" origin/main        # → 无输出
# 对侧判定入口签名里没有 admission 形参
$ git grep -n "def classify" origin/main -- '*check_delta.py'
origin/main:.../wiki-ingest/scripts/check_delta.py:138:def classify(snapshot, state, cache_dir=None, force_full=False, only=None):
# 对侧 wiki-ingest SKILL 无「准入/源排除」段（仅外链「待确认 URL」等无关措辞）
```

即对侧**根本不存在准入机制**（既无旧闸门、也无新排除表读取）。故：

- 本次反转**不会**把对侧变得更宽松（它从未拦过任何节点）；
- 但**分岔仍在，且方向反转**：此前「本侧拦下待问、对侧一律摄取」；现在「本侧仅排除 `exclude` 子树、对侧仍一律摄取」。
- **实际风险**：本侧按用户裁定 `exclude` 掉的源（含整棵项目子树及其将来新增），对侧**不认这张表** ⇒ 仍会把它当候选摄取、并可能发布进共享的 KB-AI。**这才是本单要发的主因**——排除裁定必须是两侧共识，否则形同虚设。

### 3. 不阻塞

对侧不改也不会 break 跨侧读写（契约层未变）；差别是「本侧能排除、对侧不能」。故本单**不**升级到 D1 单那种「未镜像前禁止两侧并发操作同一 KB」的纪律级别，但**建议与 D1 同批落地**。

## 三、对侧镜像清单（三档，按投入取一）

| 档 | 内容 | 何时选 |
|---|---|---|
| **A. 最小对齐（推荐先做）** | 让对侧**至少尊重远端排除表**：读 `AI_KB_SOURCE_ADMISSION_V1`（等价 `store_cli admission-list`），取 `decision=exclude` 的 token **叠加其全部后代**（子树级），命中即不摄入。默认（未裁定）纳入。 | 对侧要与本侧共用同一 KB 且允许用户用 `exclude` 作紧急刹车 |
| **B. 完整镜像** | A + 判定层全套：删「未裁定即拦」、`new` 只数内容节点 / 容器单列、`NEW_SOURCES:` 恒打印披露行、`--only` rc=3 收窄、dangling 守卫、缺页 = 空排除 rc=0、删 `admission-seed` | 对侧要把本侧 `wiki-ingest` 判定层继续对齐 |
| **C. 暂不镜像，仅记录差异** | 什么都不做，在对侧文档里写明「本侧无准入 / 不认排除表」 | 两侧短期内不会并发操作同一 KB-AI |

**选 C 时请明写**，以免将来有人误以为 `exclude` 对两侧都生效。

### 附：对侧自查锚点（名称以对侧实际为准，语义必须一致）

- **读取路径**：存在一个从控制面页取排除 token 的入口（对应本包 `store_cli admission-list`），且**缺页 ⇒ 空排除、不是错误**；**页存在但读不懂 ⇒ 硬失败**（不得当成「没有限制」）。
- **判定层**：`exclude` 命中**自身或任一祖先**即不摄入；对**容器**同样生效。
- **不要**去删远端 `AI_KB_SOURCE_ADMISSION_V1` 页、也不要改其 schema/枚举。

## 四、D1 单补遗（09-22 晚间终审修复波 `0f43a1b`）

D1 单成文于 `8e94873..b4aa89e`；其后的终审修复波 `0f43a1b` 有三项**未进 D1 单的镜像清单**。逐项标注对侧适用性：

### 补 1（★对侧适用）`overwritten_human_edits` 的 `last_seen` 必须取**写后回读值**

D1 单要求在条件更新**写成之后**才记录披露，判定条件是「当前页 revision 相对索引 `last_seen_revision_id` 前进」。修复波发现：`publisher.conditional_update` 若从**写请求的响应**取 revision，会因响应滞后得到**中间值**，导致 `overwritten_human_edits` **误报**（没覆盖却报告覆盖）。正解 = **写后回读**，`last_seen_revision_id` 取回读到的 revision。
落点：`publisher.py`（写后回读）+ 2 个新增覆盖测试。**对侧若已按 D1 单实现该披露，请一并核此处**——这是 D1 单自身的正确性补丁。

### 补 2（条件适用）corrections 候选**必须以远端当前页为基**

D1 删掉三方合并后，「只含新卡片」的候选若从空白模板重建，会**静默擦除**累积在 KB-AI 上的既有内容（红线等）；`sync_constraint_data.py` 随后还会把 `pre_output` 红线词表**重建变小**，唯一痕迹是 `overwritten_human_edits` 里的一行。
正解：steward 操作 10（corrections-promote）的候选页**必须先 fetch 当前远端页为基**（当前内容 + 新卡片），禁止空白模板重建。
落点：`agents/pb-knowledge-steward.md` 操作 10 + 约束行。
**对侧适用性**：对侧**确有** corrections 概念（实测其 `wiki-ingest/SKILL.md:128`「内容冲突登记到对应项目的 `corrections.md` 候选」）——**若对侧也存在「以新卡片重建候选」的路径，同款静默擦除风险成立**；请自查其 corrections 候选是否以远端当前页为基。

### 补 3（纯文档）lint 表格补第四检行

steward 操作 9 的表格补「索引键的页型作用域」行，与「协议四检」表头及 `schema/lint-rules.md` / wiki-ingest SKILL 的规范枚举对齐。对侧若无对应表格可忽略。
